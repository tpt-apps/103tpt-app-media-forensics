TPT App Media Forensics

1. Product Definition

Product name: TPT Media Forensics
Repository: tpt-app-media-forensics
Product family: TPT Apps
Category: Professional media inspection, forensic analysis, validation, and evidence preservation
Primary distribution: Offline desktop application
Primary target: Post-production, broadcast, media engineering, legal/evidentiary workflows, archives, security/media investigators, and technical QA
Target platforms: Windows first; Linux/macOS later

2. Executive Summary

TPT Media Forensics is an offline professional desktop application for answering a deceptively simple question:

What exactly is inside this media file, how was it produced, and is there anything technically wrong, unusual, inconsistent, or suspicious about it?

The application provides deep inspection of:

video

audio

containers

codecs

metadata

timestamps

frame structure

GOP structure

packet structure

streams

subtitles

attachments

colour information

synchronisation

corruption

discontinuities

encoding anomalies

file structure

media provenance indicators

It should not initially position itself as a consumer "AI deepfake detector." That market is crowded, difficult to validate, and prone to overclaiming.

Instead, the product should establish a much stronger technical position:

Forensic-grade inspection of media structure, timing, encoding, metadata, and integrity — performed locally.

The application should leverage the TPT media foundation:

tpt-kinetix

tpt-cadence

tpt-visual

tpt-audio

tpt-voice

tpt-av-asset

tpt-av-sync

tpt-av-test

tpt-dsp

The application is therefore a commercial layer on top of a substantial media technology stack.

6. Design Principles

6.1 Evidence before interpretation

The application must clearly distinguish:

Observed fact
Derived measurement
Heuristic finding
Interpretation

Example:

Observed:
Frame 12873 has decode timestamp discontinuity.

Derived:
Timestamp delta = -41.7 ms.

Finding:
Non-monotonic timestamp detected.

Interpretation:
Potential editing, corruption, or muxing anomaly.

The final interpretation must never be presented as fact unless the evidence supports it.

6.2 No false certainty

The application must avoid claims such as:

"This video is fake."

Instead:

"The following technical inconsistencies were detected."

This is essential for professional and legal use.

6.3 Reproducibility

A forensic analysis should be reproducible.

Record:

input hash

application version

TPT library versions

analysis profile

enabled rules

timestamps

machine-independent measurements

generated findings

A second user should be able to run the same analysis and understand how the result was produced.

6.4 Offline first

No upload should be necessary.

This is a major commercial feature for:

confidential footage

unreleased productions

legal material

corporate media

sensitive investigations

9. Case Model

A forensic analysis should be organised around a case rather than a file.

struct Case {
    id: CaseId,
    name: String,
    description: Option<String>,
    assets: Vec<AssetId>,
    analyses: Vec<AnalysisId>,
    findings: Vec<FindingId>,
    evidence: Vec<EvidenceId>,
    reports: Vec<ReportId>,
}

One case may contain:

original.mp4
edited.mp4
reference.mov
audio.wav
export.mp4
screenshots
notes

This allows comparison between related media.

10. Asset Model

struct MediaAsset {
    id: AssetId,
    path: PathBuf,
    size_bytes: u64,
    hashes: HashSet,
    media_type: MediaType,
}

Hashes should initially include:

SHA-256

Potential additional hashes:

SHA-512

BLAKE3

BLAKE3 is useful for high-speed local processing, while SHA-256 is useful for interoperability.

55. Large File Handling

The application must support very large media files.

Requirements:

cancellation

Never load a multi-gigabyte media file into RAM simply to inspect it.

56. Parallelism

Parallelise independent work:

       │
       ├── metadata
       ├── video
       ├── audio
       └── timing

However, decoding must respect codec/threading constraints.

The application should avoid oversubscribing CPU cores.

57. Performance Targets

Target:

UI remains responsive during analysis.

Analysis can use all available CPU cores where safe.

Large files stream rather than requiring full memory residency.

Cancellation should respond within a few seconds.

Batch mode should maintain high throughput.

Repeated analyses should benefit substantially from caching.

Performance benchmarks must use representative media rather than synthetic tiny files.

71. Rule Explainability

Every finding should have an explanation.

Example:

VIDEO.FRAME_RATE_CHANGE

What it checks:
Whether measured frame timing changes beyond the configured tolerance.

Why it matters:
Unexpected changes may indicate cadence conversion,
editing, encoding behaviour, or malformed timestamps.

Observed:
29.97 fps → 30.00 fps

Limitations:
This finding alone does not establish manipulation.

This is important for professional credibility.

The deterministic parts of analysis should produce identical results across runs.

Avoid:

random sampling without recorded seeds
